# Техническое задание на разработку отчёта по поставкам/продажам Wildberries

## 1. Назначение и цели

Разработать отчёт в формате Excel по поставкам товара на склады Wildberries. 
Отчёт строится в разрезе «поставка + товар» и содержит данные о поступлении, продажах, возвратах и остатках.

**Цели:**

- Автоматизировать сбор данных о поставках через API Wildberries.
- Свести данные из двух источников (supplies-api и statistics-api) в единый отчёт.
- Обеспечить фильтрацию по конкретным идентификаторам поставок.

---

## 2. Источники данных

### 2.1. Supplies API

**Базовый URL:** `https://supplies-api.wildberries.ru/api/v1/supplies`

| GET | `/api/v1/supplies/{ID}/goods` | Возвращает список товаров, поступивших по поставке |

### 2.2. Statistics API

**URL:** `https://statistics-api.wildberries.ru/api/v1/supplier/sales`

Метод возвращает информацию о продажах и возвратах. Одна строка ответа = один заказ = одна единица товара.

**Параметры запроса:**

- `dateFrom` — дата начала периода (обязательный).
- `dateTo` — дата окончания периода.
- `limit` — ограничение количества строк.

**Используемые поля ответа:**

| Поле | Описание |
|---|---|
| `incomeID` | Идентификатор поставки |
| `nmId` | Идентификатор товара (номенклатуры) |
| `isSupply` | Признак возврата (`true` — возврат на склад) |
| `isRealization` | Признак продажи (`true` — товар продан) |
| `date` | Дата операции |
| `lastChangeDate` | Дата последнего изменения |

## 3. Авторизация

- supplies-api — заголовок `Authorization` с токеном доступа к разделу поставок.
- statistics-api — заголовок `Authorization` с токеном статистики.
- Токены передаются в виде значений без префикса (по текущей схеме WB API).

---

## 4. Логика работы

### 4.1. Входные параметры

| Параметр | Тип | Описание |
|---|---|---|
| `TARGET_INCOME_IDS` | `list[int]` | Список идентификаторов поставок, по которым строится отчёт |
| `TOKEN_SUPPLIES` | `str` | Токен авторизации для supplies-api |
| `TOKEN_STATISTICS` | `str` | Токен авторизации для statistics-api |

### 4.2. Алгоритм

**Шаг 1. Получение информации о поставках**

Для каждого `incomeID` из `TARGET_INCOME_IDS`:

1. Выполнить GET-запрос к `/api/v1/supplies/{ID}` — получить `supplyDate`.
2. Выполнить GET-запрос к `/api/v1/supplies/{ID}/goods` — получить список товаров.
3. Для каждого товара из ответа извлечь `nmID` и `quantity`.
4. Сгруппировать данные по ключу `(incomeID, nmID)`, суммируя `quantity` при повторах.

**Шаг 2. Определение периода для запроса продаж**

1. `DATE_FROM` = минимальное значение `supplyDate` среди всех запрошенных поставок.
2. `DATE_TO` = текущая дата.
3. Если `supplyDate` не получен ни по одной поставке — использовать фолбэк: последние 90 дней от текущей даты.

**Шаг 3. Получение данных о продажах и возвратах**

1. Выполнить GET-запрос к `/api/v1/supplier/sales` с параметрами `dateFrom`, `dateTo`, `limit`.
2. Отфильтровать строки, где `incomeID` входит в `TARGET_INCOME_IDS`.
3. Для каждой строки определить тип операции:
   - `isRealization == True` → продажа.
   - `isSupply == True` → возврат.
4. Сгруппировать по ключу `(incomeID, nmID)`:
   - Подсчитать количество проданных единиц.
   - Подсчитать количество возвращённых единиц.
   - Зафиксировать максимальную дату продажи (поле `date`, при отсутствии — `lastChangeDate`).
   - Зафиксировать максимальную дату возврата (аналогично).

**Шаг 4. Формирование итоговой таблицы**

1. Объединить все ключи `(incomeID, nmID)` из данных о поставках и продаж.
2. Для каждого ключа рассчитать:
   - `Актуальное кол-во товара на складе` = `Поступило` − `Продано`.
3. Сформировать DataFrame и выгрузить в Excel.

### 4.3. Обработка ошибок

| Ситуация | Действие |
|---|---|
| Ошибка HTTP при запросе информации о поставке | Логировать ошибку, продолжить обработку остальных поставок |
| Ошибка HTTP при запросе товаров поставки | Логировать ошибку, продолжить обработку остальных поставок |
| Ошибка HTTP при запросе продаж | Вывести сообщение об ошибке, завершить работу |
| Пустой список `TARGET_INCOME_IDS` | Вывести предупреждение, завершить работу |
| Нет данных для отчёта | Вывести сообщение, завершить работу |

## 5. Формат выходного файла

**Формат:** Excel (`.xlsx`).
**Имя файла:** `wb_supply_report.xlsx`.
**Без индексной колонки** (`index=False`).

### Структура таблицы

| Колонка | Описание | Источник |
|---|---|---|
| Идентификатор поставки | `incomeID` | supplies-api |
| Дата поставки | `supplyDate` | supplies-api (`/supplies/{ID}`) |
| Идентификатор товара | `nmID` | supplies-api (`/supplies/{ID}/goods`) и statistics-api |
| Кол-во товара в поставке | Сумма `quantity` по товару в поставке | supplies-api (`/supplies/{ID}/goods`) |
| Кол-во проданного товара | Количество строк с `isRealization == True` | statistics-api |
| Кол-во возвращенного товара | Количество строк с `isSupply == True` | statistics-api |
| Фактическое кол-во товара на складе | Поступило − Продано | Расчётное |
| Максимальная дата продажи | Последняя дата среди строк с `isRealization == True` | statistics-api |
| Максимальная дата возврата | Последняя дата среди строк с `isSupply == True` | statistics-api |

## 6. Ограничения и допущения

1. Поле `quantity` из ответа `/supplies/{ID}/goods` используется как «количество поступивших товаров». При необходимости может быть заменено на `acceptedQuantity`.
2. Возвраты (`isSupply == True`) не вычитаются из остатка. Формула остатка: `Поступило − Продано`.
3. Пагинация в запросе продаж не реализована. При большом объёме данных требуется доработка с параметром `offset`.
4. Токены для supplies-api и statistics-api могут совпадать или различаться — в зависимости от настроек личного кабинета WB.
